# Phase 05.1: User Management System — Research

**Researched:** 2026-05-22
**Domain:** PostgreSQL role hierarchy, Express middleware authorization, vanilla JS permission UI
**Confidence:** HIGH

---

## Summary

Phase 05.1 extends the existing Express + Passport + PostgreSQL monolith with a 3-tier role system: SuperAdmin (single), Group Admin (one per niche cluster), and Group User (belongs to exactly one Group Admin). This is a validation phase — all changes land in the monolith (`server.js`, `routes/`, `services/`, `db/migrate.js`), not in the microservices layer. No Hono, Drizzle, or monorepo packages are involved.

The existing schema already has `users.role VARCHAR(20)` (`admin` | `user`) and a working invite flow. The migration strategy is additive: add new columns and tables without dropping anything. The existing `admin` role maps to SuperAdmin; all existing `user` records map to Group User with a synthetic Group Admin created for the current owner. Data isolation is already implemented at the query level (`WHERE user_id = $1`) — extending this to Group Admin scoping means replacing the literal `user_id` filter with a set-based filter derived from group membership.

**Primary recommendation:** Use a single `user_permissions` JSONB column on `users` for per-user permission toggles (set by Group Admin), and a `group_admin_id UUID REFERENCES users(id)` FK column on `users` for group membership. Avoid a separate `permissions` table — it adds joins without benefit for this use case at this scale.

## Architecture Patterns

### Recommended Schema Changes

```sql
-- 1. Extend role enum (VARCHAR — no Postgres ENUM, so just update CHECK or docs)
-- Existing: 'admin' | 'user'
-- New values: 'super_admin' | 'group_admin' | 'group_user'
-- Migration: UPDATE users SET role = 'super_admin' WHERE role = 'admin'
--            UPDATE users SET role = 'group_user'  WHERE role = 'user'

ALTER TABLE users ADD COLUMN IF NOT EXISTS group_admin_id UUID REFERENCES users(id) ON DELETE SET NULL;
-- NULL = SuperAdmin or Group Admin (not a member of another admin's group)
-- non-NULL = Group User, points to their Group Admin

ALTER TABLE users ADD COLUMN IF NOT EXISTS permissions JSONB NOT NULL DEFAULT '{}'::jsonb;
-- Stores per-user capability flags set by Group Admin
-- Shape: { "add_products": true, "edit_products": false, ... }

-- Invitations need to carry the intended role for the invitee
ALTER TABLE invitations ADD COLUMN IF NOT EXISTS invited_role VARCHAR(20) NOT NULL DEFAULT 'group_user';
-- 'group_admin' when SuperAdmin sends invite
-- 'group_user'  when Group Admin sends invite

-- Group Admin needs to be recorded on the invitation so the OAuth callback knows
-- which group the new user belongs to
ALTER TABLE invitations ADD COLUMN IF NOT EXISTS group_admin_id UUID REFERENCES users(id) ON DELETE SET NULL;
```

### Roles and Their SQL Meanings

| Role | `role` value | `group_admin_id` |
|------|-------------|-----------------|
| SuperAdmin | `super_admin` | NULL |
| Group Admin | `group_admin` | NULL |
| Group User | `group_user` | UUID of their Group Admin |

### Pattern 1: Role Middleware Guards

Replace the existing local `isAdmin` guards across routes with shared middleware in `middleware/auth.js` (new file):

```javascript
// middleware/auth.js
function isSuperAdmin(req, res, next) {
  if (req.user?.role === 'super_admin') return next();
  res.status(403).json({ success: false, error: 'Forbidden' });
}

function isGroupAdminOrAbove(req, res, next) {
  const { role } = req.user || {};
  if (role === 'super_admin' || role === 'group_admin') return next();
  res.status(403).json({ success: false, error: 'Forbidden' });
}

function requirePermission(perm) {
  return (req, res, next) => {
    const { role, permissions } = req.user || {};
    // SuperAdmin and Group Admin always pass
    if (role === 'super_admin' || role === 'group_admin') return next();
    // Group User: check their JSONB permissions
    if (permissions?.[perm] === true) return next();
    res.status(403).json({ success: false, error: 'Forbidden' });
  };
}

module.exports = { isSuperAdmin, isGroupAdminOrAbove, requirePermission };
```

### Pattern 2: Group Scoping Middleware

Group Admins must only see data belonging to users in their group. Attach a resolved `allowedUserIds` array to `req` for use in WHERE clauses:

```javascript
// middleware/scopeGroup.js
const { query } = require('../db');

/**
 * Resolves the set of user IDs the current user is allowed to see.
 * SuperAdmin: all users (pass-through, no filter applied)
 * Group Admin: [self] + all group_user rows WHERE group_admin_id = self.id
 * Group User: [self] only
 *
 * Sets req.scopedUserIds = UUID[] or null (null = no filter, SA sees all)
 */
async function scopeGroup(req, res, next) {
  const { id, role } = req.user;
  if (role === 'super_admin') {
    req.scopedUserIds = null; // no filter
    return next();
  }
  if (role === 'group_admin') {
    const { rows } = await query(
      `SELECT id FROM users WHERE id = $1 OR group_admin_id = $1`,
      [id]
    );
    req.scopedUserIds = rows.map(r => r.id);
    return next();
  }
  // group_user — own data only
  req.scopedUserIds = [id];
  next();
}

module.exports = { scopeGroup };
```

Then in route queries, use:

```javascript
// When scopedUserIds is null → no user filter (SA sees all)
// When array → WHERE user_id = ANY($1::uuid[])
const filter = req.scopedUserIds
  ? `AND user_id = ANY($2::uuid[])`
  : '';
const params = req.scopedUserIds
  ? [subjectId, req.scopedUserIds]
  : [subjectId];
```

### Pattern 3: Invite Flow Changes

The existing invite flow stores `email` + `token` + `invited_by`. It needs two new columns:

- `invited_role` — which role the invitee will receive on account creation
- `group_admin_id` — for Group User invites, which Group Admin they belong to

OAuth callback change in `server.js` (in the `GoogleStrategy` handler):

```javascript
// After validateToken(inviteToken):
const newRole = inv.invited_role || 'group_user';
const groupAdminId = inv.group_admin_id || null;

user = await createUser({
  googleId: profile.id,
  email,
  name: profile.displayName,
  photo: profile.photos?.[0]?.value,
  role: newRole,
  groupAdminId,
});
```

`createUser` in `userService.js` must be updated to accept `role` and `groupAdminId` parameters instead of hardcoding the admin-email check.

### Pattern 4: Per-User Permissions JSONB

The 7 permission keys:

```javascript
const DEFAULT_PERMISSIONS = {
  add_products:      false,
  edit_products:     false,
  delete_products:   false,
  view_logs:         false,
  trigger_send:      false,
  manage_schedules:  false,
  view_settings:     false,
};
```

Group Admin sets these via `PUT /api/users/:id/permissions` (new route). The server reads `req.user.permissions.add_products` on every relevant request. Since `deserializeUser` re-fetches user from DB (with 60s TTL cache), permission changes propagate within 60 seconds — no re-login required.

### Pattern 5: Remove Group User — "Keep or Delete?" Flow

```
DELETE /api/users/:id?keepProducts=true|false
```

Route logic:

```javascript
if (keepProducts === 'true') {
  // Re-assign products to the Group Admin before deleting user
  await query(
    `UPDATE products SET user_id = $1 WHERE user_id = $2`,
    [groupAdminId, targetUserId]
  );
} else {
  // Products cascade delete (already: ON DELETE CASCADE on user_id FK)
}
await deleteUser(targetUserId);
```

### Anti-Patterns to Avoid

- **Separate permissions table:** Adds joins without benefit for 7 boolean flags. JSONB on users is simpler and fast enough for this scale.
- **Client-side role trust:** Never accept `role` from request body to authorize actions. Always read `req.user.role` (sourced from DB via deserializeUser).
- **Blocking on scopeGroup for SA:** SuperAdmin routes must not issue a `SELECT id FROM users` query just to set `scopedUserIds = null`. Check role first, short-circuit immediately.
- **Cache poisoning after permission change:** When Group Admin updates a Group User's permissions, call `_cacheInvalidate(targetUser.googleId)` in `userService.js` so the next request re-fetches from DB.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Permission enforcement | Custom session checks scattered across routes | `requirePermission('add_products')` middleware | Single enforcement point, easy to audit |
| Group membership lookup | Ad-hoc JOIN in each route | `scopeGroup` middleware sets `req.scopedUserIds` once | Prevents missed scoping bugs |
| Cache invalidation | Manual cache clearing scattered across code | Always call `_cacheInvalidate(googleId)` in `userService.updateUserById` | Cache is already in userService — put invalidation there |

## Common Pitfalls

### Pitfall 1: Existing `isAdmin` Guards Spread Across Multiple Files

**What goes wrong:** `routes/users.js` defines its own local `isAdmin`. `server.js` has another. After adding `super_admin`, `group_admin`, both need updating everywhere.

**How to avoid:** Create `middleware/auth.js` with canonical guards. Find/replace all local `isAdmin` functions. There are currently at least 2: `server.js:101` and `routes/users.js:8`.

**Warning signs:** A Group Admin can access SuperAdmin-only routes.

### Pitfall 2: `createUser` Hardcodes Role Assignment

**What goes wrong:** `userService.createUser` checks `email === ADMIN_GOOGLE_EMAIL` to decide role. After this phase, role comes from the invitation record, not email matching.

**How to avoid:** Accept explicit `role` and `groupAdminId` params in `createUser`. Bootstrap logic stays in the OAuth callback (only invoked when no invite token and email matches `ADMIN_GOOGLE_EMAIL`).

### Pitfall 3: Permission Cache Not Invalidated on Update

**What goes wrong:** Group Admin updates Group User's permissions via API. User's next request still uses cached `permissions: {}` from 60s-TTL cache.

**How to avoid:** In `userService.updateUserById` (called by the permissions update route), `_cacheInvalidate(user.googleId)` is already called IF the user object has `googleId`. Confirm the returned user from DB has `google_id` populated before relying on this.

### Pitfall 4: Group Admin Seeing Other Group Admins' Data

**What goes wrong:** `scopeGroup` query `WHERE id = $1 OR group_admin_id = $1` — if a Group User is somehow assigned to the wrong Group Admin (data integrity issue), their data bleeds across groups.

**How to avoid:** Add a unique constraint: a `group_user` must have `group_admin_id IS NOT NULL`. Add a CHECK constraint on `users`: `CONSTRAINT users_group_user_has_admin CHECK (role != 'group_user' OR group_admin_id IS NOT NULL)`. This enforces at the DB level.

### Pitfall 5: Migration Breaks Existing Sessions

**What goes wrong:** After renaming roles from `admin`→`super_admin` and `user`→`group_user`, existing authenticated sessions have a user object with `role: 'admin'` cached in memory. The `isAdmin` guard check `role === 'admin'` suddenly returns false.

**How to avoid:** Migrate role values in the DB first with a single UPDATE. Then update all middleware checks in the same deploy. The 60s TTL cache means stale values persist briefly — add backward-compat for up to 60s by checking both old and new role values during the first deploy, or do a rolling restart to clear in-process caches.

**Simpler option:** Keep `role = 'admin'` as the SuperAdmin DB value and only add `group_admin` / `group_user` as new values. Map existing `user` → `group_user`. This avoids renaming `admin` and preserves all existing `isAdmin` guards without change. Then add new guards on top.

**Recommendation:** Do NOT rename `admin` to `super_admin`. Keep `admin` as the SuperAdmin DB value. Only add two new roles: `group_admin` and `group_user`. Map existing `user` → `group_user` (single UPDATE). Existing `isAdmin` guards in server.js and routes/users.js continue to work for SuperAdmin without modification.

## Code Examples

### Migration Additions (idempotent)

```javascript
// db/migrate.js — append to existing migrate() function
await query(`ALTER TABLE users ADD COLUMN IF NOT EXISTS group_admin_id UUID REFERENCES users(id) ON DELETE SET NULL`);
await query(`ALTER TABLE users ADD COLUMN IF NOT EXISTS permissions JSONB NOT NULL DEFAULT '{}'::jsonb`);
await query(`ALTER TABLE invitations ADD COLUMN IF NOT EXISTS invited_role VARCHAR(20) NOT NULL DEFAULT 'group_user'`);
await query(`ALTER TABLE invitations ADD COLUMN IF NOT EXISTS group_admin_id UUID REFERENCES users(id) ON DELETE SET NULL`);

// Migrate existing 'user' role to 'group_user'
await query(`UPDATE users SET role = 'group_user' WHERE role = 'user'`);

// Index for group membership lookups
await query(`CREATE INDEX IF NOT EXISTS users_group_admin_id ON users(group_admin_id)`);
```

### New Route: List Group Users (Group Admin)

```javascript
// GET /api/users/group — Group Admin sees their users; SuperAdmin sees all
router.get('/group', isGroupAdminOrAbove, async (req, res) => {
  const { id, role } = req.user;
  let rows;
  if (role === 'admin') {
    ({ rows } = await query(`SELECT id, email, name, photo, role, permissions, group_admin_id, status FROM users ORDER BY created_at ASC`));
  } else {
    ({ rows } = await query(
      `SELECT id, email, name, photo, role, permissions, group_admin_id, status FROM users WHERE group_admin_id = $1 ORDER BY created_at ASC`,
      [id]
    ));
  }
  res.json({ success: true, users: rows });
});
```

### New Route: Update Group User Permissions

```javascript
// PUT /api/users/:id/permissions
router.put('/:id/permissions', isGroupAdminOrAbove, async (req, res) => {
  const { permissions } = req.body; // { add_products: true, view_logs: false, ... }
  const target = await findUserById(req.params.id);
  if (!target) return res.status(404).json({ success: false, error: 'User not found' });

  // Group Admin can only update users in their own group
  if (req.user.role === 'group_admin' && target.groupAdminId !== req.user.id) {
    return res.status(403).json({ success: false, error: 'Forbidden' });
  }

  await query(
    `UPDATE users SET permissions = $1, updated_at = NOW() WHERE id = $2`,
    [JSON.stringify(permissions), target.id]
  );
  if (target.googleId) _cacheInvalidate(target.googleId);
  res.json({ success: true });
});
```

## Open Questions

1. **SuperAdmin can see all groups' data — is a "view as Group Admin" mode needed?**
   - What we know: SuperAdmin's `scopedUserIds = null` means unrestricted access.
   - What's unclear: Whether the UI should let SA switch to a group admin's view.
   - Recommendation: Defer. Not in the stated requirements. SA sees everything in this phase.

2. **What happens to the existing invite link in production when `invited_role` defaults to `group_user`?**
   - What we know: `ALTER TABLE` with `DEFAULT 'group_user'` applies to new rows; existing pending invitations get NULL on the new column (unless backfilled).
   - Recommendation: The migration SQL should include `UPDATE invitations SET invited_role = 'group_user' WHERE invited_role IS NULL` as a backfill step, but since `NOT NULL DEFAULT` is set in the ADD COLUMN statement, existing rows get the default automatically in PostgreSQL. Verify behavior before shipping.

3. **Should Group Admin be allowed to edit their own profile (name, email)?**
   - Recommendation: Not in scope for this phase. The `PUT /api/users/me` endpoint (if it exists) stays as-is.
